ZAMP - AI SOLUTIONS ANALYST CASE STUDY
Chosen problem: PS-1  Invoice processing - from PDF to decision
Name of the build: "Ledgerline" (AP invoice desk)
Status: built and tested (42 automated tests + real-browser run). See README.md.

0. WHY PS-1 (and not PS-2 / PS-3)
---------------------------------------------------------------------
- PS-1 is Zamp's own core work (AP automation), so the demo talks
  straight to what the interviewers do every day.
- The decision is rule-based and can be explained line by line.
  A rule engine gives the same answer every run, so the live demo
  will not surprise us.
- PS-3 depends on live web research (LinkedIn, news). That is the
  part most likely to break or change during a live demo.
- PS-2 is good too, but PS-1 has richer edge cases (scanned PDFs,
  split POs, duplicates, tolerances, tax styles).

2. ASSUMPTIONS (noted, as the FAQ asks)
---------------------------------------------------------------------
- Company is Indian; currency INR; tax is GST (CGST+SGST inside the
  state, IGST across states). Vendors have a GSTIN (15 chars, with a
  check digit we can verify).
- 2-way match (invoice vs PO). Goods receipt (3-way match) is out of
  scope; listed as "next step".
- Procurement data = CSV files we create (vendors, POs, PO lines) +
  a ledger of invoices already processed (SQLite).
- Input = one invoice PDF per run (upload, or pick a prepared sample).
  Email inbox intake is "next step"; upload stands in for it.
- Only APPROVED invoices use up PO balance. Invoices waiting for review
  are shown as "pending" against the PO but do not block others.
- AI never makes the decision. AI only reads the document. The
  decision is made by fixed rules so it is explainable and repeatable.


3. PROCESS MAP (input -> stages -> decision -> output)
---------------------------------------------------------------------
INPUT: invoice PDF

 [1] INTAKE
     - save file, compute SHA-256 hash, count pages
     - detect: has text layer?  or scanned image?
     - same hash seen before?  -> remember for the duplicate stage
 [2] EXTRACT
     - Gemini reads the PDF -> JSON: vendor name, GSTIN, invoice no,
       dates, PO reference, line items, subtotal, taxes, total,
       tax-inclusive or not, + notes on anything it could not read
       (the AI is told to return null rather than guess)
     - if AI fails: local text parser (text PDFs only)
     - if scanned AND AI fails -> cannot read -> Needs review
 [3] VALIDATE THE DOCUMENT
     - required fields present? (invoice no, date, total, vendor)
     - maths: lines = subtotal, subtotal + tax = total (Rs 1 slack)
     - dates: not in the future, not older than 180 days
     - GSTIN format + check digit
 [4] VENDOR CHECK
     - match by GSTIN -> else by cleaned name (fuzzy)
     - vendor blocked / not in master -> Reject
     - name matches but GSTIN differs -> Reject (possible impersonation)
     - bank account differs from master -> Needs review (call-back check)
 [5] DUPLICATE CHECK  (runs before PO matching, as in real AP)
     - same vendor + same cleaned invoice number, already approved or
       pending -> Reject
     - same number but the earlier one was rejected -> Needs review
       (resubmission)
     - same file hash -> Reject
     - same vendor + same total + date within 10 days, different
       number -> Needs review (possible re-send)
 [6] PO MATCH
     - PO number on invoice -> clean it -> look it up
       (PO-2026-0101 / PO 101 / 2026/0101 all mean the same)
     - PO belongs to a different vendor -> Reject
     - PO closed -> Needs review
     - no PO number -> score open POs of the vendor by line items +
       amount -> suggest best one -> Needs review (never auto-approve
       on an inferred PO)
 [7] LINE + AMOUNT MATCH
     - each invoice line matched to a PO line (description similarity)
     - price or quantity unreadable -> Needs review (never approve on
       a guessed number)
     - unit price within tolerance? quantity within what is left?
     - cumulative: already billed on PO + this invoice <= PO value (+1%)
       (if the excess is only the price variance already flagged, it is
       a note, not a second failure)
     - GST rate matches the PO
 [8] DECIDE
     - any REJECT rule failed       -> REJECTED
     - else any REVIEW rule failed  -> NEEDS REVIEW
     - else                         -> APPROVED
     - write plain-English reasons + a note to the vendor if rejected,
       or a note to the reviewer if held
 [9] RECORD
     - save run, every stage, every check, the decision
     - approved -> added to PO ledger (uses up PO balance)
     - reviewer can later Approve / Reject a held invoice from the UI
       (with a note); that also updates the ledger

OUTPUT: decision (Approved / Needs review / Rejected) + reasons +
        full trail of what happened at each stage.


4. EDGE CASES WE BUILD (realistic, not trivial)
---------------------------------------------------------------------
 HAPPY  Clean text PDF, explicit PO, prices match, GST split as
        CGST+SGST                                    -> APPROVED

 EC-1   SPLIT PO, OVER-BILLED. PO worth Rs 4,00,000 was already billed
        Rs 2,50,000 (part 1, in the ledger). Part 2 asks Rs 1,80,000.
        Each invoice alone looks fine; together they are Rs 30,000
        over.                                        -> NEEDS REVIEW
        (shows: process remembers history, not just this document)

 EC-2   DUPLICATE RE-SEND. Vendor re-sends an already-paid invoice,
        number written "INV/24-25/0457" instead of "INV-24-25-457",
        new date on top.                             -> REJECTED
        (shows: cleaning of identifiers, not exact string match)

 EC-3   SCANNED INVOICE, NO PO NUMBER, TAX INCLUDED IN PRICES.
        Image-only PDF (no text layer). AI reads it. PO is inferred
        from vendor + line items.                    -> NEEDS REVIEW
        with "Suggested PO: PO-2026-0104 (3 of 3 lines match)"
        (shows: messy input + judgment not to auto-approve a guess)

 EC-4   VENDOR IMPERSONATION. Invoice says "Sharma Office Supplies"
        (an approved vendor) but GSTIN and bank account are different
        from the vendor master.                      -> REJECTED
        (shows: fraud control - identity is checked by tax ID, not name)

 BONUS  PRICE CREEP. One line's unit price is 6% above PO price
        (other lines fine).                          -> NEEDS REVIEW
        with the exact variance shown per line.

 Also handled without a special file: unknown vendor, PO of another
 vendor, closed PO, future date, maths that does not add up, AI down.


5. HOW WE BUILD IT (stack)
---------------------------------------------------------------------
- Backend: Python + FastAPI. One service serves both API and UI.
- Storage: SQLite (runs, stage events, checks, invoice ledger).
  Master data in CSV (vendors.csv, purchase_orders.csv, po_lines.csv).
- AI: Gemini API (reads PDF directly, also scans). Strict JSON
  schema output. Responses cached by file hash so a re-run of the
  same file gives the same result and costs nothing.
- Local fallback: PyMuPDF text + regex parser.
- Live run view: the pipeline runs in a background thread and writes
  each stage event to the DB; the browser listens with Server-Sent
  Events (SSE) and lights up each stage as it really finishes.
  No fake timers.
- UI: plain HTML/CSS/JS (no build step), designed with the
  frontend-design skill. Screens:
    a) New run  - drop a PDF or pick a sample; live stage view
    b) Run detail - PDF preview | extracted fields | checks | decision
    c) Dashboard - history of runs, status counts, filters,
       review queue, approve/reject held items
    d) Reference data - vendors, POs with billed / left balance
    e) "Reset demo data" button (so the demo can be run again from
       a clean ledger - duplicates/split-PO checks remember history)
- Test inputs: generated with reportlab (text PDFs) + a rendered
  image-only PDF for the scan.
- Deploy later: Dockerfile; same app can go to Render.


6. TEST PLAN
---------------------------------------------------------------------
- Unit tests: GSTIN checksum, invoice/PO number cleaning, tolerance
  maths, decision rules.
- End-to-end tests through the real HTTP API: upload each sample
  PDF, wait for the run, assert the expected decision.
- Run the full demo order twice (with reset in between) to make sure
  the demo works again and again.
- Run once with the AI switched off to show the fallback path.
- Browser check of all screens at desktop and phone width.
